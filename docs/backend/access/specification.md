# Сервис доступа — спецификация модели данных

Проект схемы для первого этапа реализации. Общие требования к сервису описаны в [спецификации проекта](../../specification.md#аккаунты-и-роли).

## Согласованные правила

- У каждого аккаунта одна роль. Пользователь входит по выданному логину и паролю. Для первой версии достаточно логина, поэтому ФИО в схему пока не включаем. Логин приводим к нижнему регистру при создании аккаунта и входе.
- Ученики решают задачи без аккаунта. Аккаунты предусмотрены для составителей заданий, представителей и проверяющих.
- Начальные роли вносит миграция. Отдельный интерфейс администрирования и настройка справочника ролей через сайт пока не входят в этот этап.
- Каждый успешный вход создаёт отдельную сессию на семь дней с момента входа. При выходе с одного устройства сессии на других устройствах продолжают действовать.
- Сервис выдаёт случайный токен и хранит его хеш. При каждой проверке доступа сервис читает текущую роль аккаунта, в том числе при использовании ранее выданного токена.

## Проект схемы

Аккаунт ссылается на одну запись справочника ролей. Одна роль может быть назначена нескольким аккаунтам. У аккаунта может быть несколько сессий. Все таблицы находятся в базе `access`.

### `roles` — справочник ролей

| Поле | Назначение и ограничения |
|---|---|
| `id` | Первичный ключ. |
| `code` | Уникальный обязательный код роли. Его использует сервис при проверке доступа. |
| `name` | Обязательное отображаемое название роли. |

### `accounts` — аккаунты

| Поле | Назначение и ограничения |
|---|---|
| `id` | Первичный ключ. Предлагаемый тип — UUID. |
| `login` | Обязательный логин, уникальный после приведения к нижнему регистру. |
| `password_hash` | Обязательный хеш пароля. |
| `role_id` | Обязательный внешний ключ на `roles.id`. |
| `created_at`, `updated_at` | Время создания и последнего изменения аккаунта с часовым поясом. |

### `sessions` — сессии входа

| Поле | Назначение и ограничения |
|---|---|
| `id` | Первичный ключ. Предлагаемый тип — UUID. |
| `account_id` | Обязательный внешний ключ на `accounts.id`. |
| `token_hash` | Обязательный уникальный хеш выданного токена. |
| `created_at` | Время создания сессии с часовым поясом. |
| `expires_at` | Время окончания сессии с часовым поясом. Рассчитывается при входе. |
| `revoked_at` | Время отзыва сессии с часовым поясом. Поле пустое, пока её не отозвали. |

## Открытые вопросы

1. Кто создаёт аккаунты на первом этапе. Общая спецификация поручает это администратору. Предлагаемый вариант — сохранить служебную роль `admin`, создать первый аккаунт отдельной командой и пользоваться API для создания остальных аккаунтов.
2. Как проверять формат логина. Предлагаемый вариант — от 3 до 32 символов, латинские буквы, цифры, точка, дефис и подчёркивание. Первый символ — буква или цифра. Пробелы по краям убираем перед сравнением. Пробелы внутри логина отклоняем.
3. Как проверять пароль при создании аккаунта. Предлагаемый вариант — минимум 15 символов и максимум 72 байта в UTF-8 при использовании bcrypt. Пароль проверяем целиком, без обрезки и смены регистра. Разрешены пробелы и кириллица.
