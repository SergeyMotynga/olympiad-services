# Backend на Python

Применяй вместе с [общим backend-harness](../../AGENTS.md) и его архитектурными принципами. Этот профиль сохраняет личные Python-соглашения; существующие решения проекта имеют приоритет.

## Структура

При создании нового Python-backend без заданной структуры используй три основных слоя:

```text
API / transport -> Services -> Repositories / persistence
```

Обязанности и границы транзакций определены в [общем профиле](architecture.md#ответственность): транспорт вызывает сервис, сервис координирует бизнес-сценарий, репозиторий выполняет операции с хранилищем. Для небольшой реализации достаточно функций и модулей; классы появляются при необходимости состояния или полезного интерфейса.

Вспомогательные модули выбирай по потребности:

- **Transport schemas:** форма и типы запросов/ответов, сериализация и проверки входного формата. Бизнес-правила действуют и при вызове сценария через другой транспорт.
- **DTO:** внутренние контракты передачи данных, когда отдельный контракт полезен. Следуй принятому способу передачи DTO и ORM-объектов; внутренние контракты отделены от HTTP-схем.
- **Validators:** переиспользуемые проверки и нормализация доменных значений. Проверки с обращением к хранилищу координируются сервисом.
- **Domain:** понятия предметной области, значения и инварианты.
- **Models:** представление данных для используемого хранилища или ORM.
- **Exceptions:** содержательные ошибки бизнес-сценариев; преобразование в HTTP-статусы и ответы относится к API.

Эти модули поддерживают основные слои; каждый сценарий использует только необходимые части. Имена каталогов следуют соглашениям проекта.

## Ошибки, зависимости и ресурсы

- Используй принятые доменные исключения и сохраняй причину ошибки при преобразовании через `raise ... from ...`. Обрабатывай исключение там, где можно принять осмысленное решение; общий перехват с успешным ответом скрывает сбой.
- Используй выбранные проектом фреймворк, ORM и способ получения зависимостей. Профиль не предписывает FastAPI, Pydantic, SQLAlchemy или DI-контейнер.
- Владелец сессии или другого ресурса обеспечивает закрытие через принятый context manager или `try/finally`; транзакция охватывает согласованный сценарий.
- Сохраняй принятый синхронный или асинхронный способ выполнения. В async-коде используй совместимый I/O, обеспечивай освобождение ресурсов при отмене и сохраняй распространение `CancelledError` после очистки.

## TDD и проверки

Применяй обязательный цикл из [правил проекта](../../AGENTS.md#обязательный-tdd) средствами проекта. Используй его test runner, фикстуры, проверки типов и форматирования из конфигурации и CI. Не вводи другой стек тестирования ради подключения профиля. Проверяй поведение через публичные границы; взаимодействие ORM, транзакций и реальной БД проверяй интеграционно, когда изменение затрагивает их семантику.
